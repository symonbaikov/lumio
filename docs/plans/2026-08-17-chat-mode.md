# Chat Mode — «Expensify-style» упрощённый режим приложения

Пользователь общается с приложением только через чат. ИИ сам вызывает нужные действия
(создать расход, категоризировать, загрузить стейтмент, показать отчёт), а сложный
интерфейс в этом режиме скрыт полностью.

## Ключевые решения

### Р1. Где крутится модель — гибрид за одним интерфейсом
Текущая архитектура — только локальная WebLLM (≤9B). Такие модели ненадёжны в
многошаговом tool calling. Решение:

- Агентный цикл пишем против **OpenAI-совместимого интерфейса** (`chat.completions.create`
  с `tools`) — WebLLM его уже поддерживает.
- **MVP — локальная модель** с *ограниченной* схемой интентов (см. Р2) — свойство
  «данные не покидают инстанс» сохраняется.
- **Опционально (этап 7)** — BYO-key облачный провайдер (Anthropic/OpenAI-совместимый)
  через backend-прокси за тем же интерфейсом, выключен по умолчанию, включается
  в настройках workspace с явным предупреждением о передаче данных наружу.

### Р2. Формат вызова действий — constrained intents, не свободный tool calling
Малые модели плохо соблюдают произвольные JSON-схемы. Вместо N независимых tools —
один структурированный ответ модели: `{ reply: string, action?: { name, params } }`,
где `name` — из закрытого перечня, `params` валидируются zod-схемой инструмента
(схемы берём из `mcp-server/src/tools/*`). Невалидный интент → одна повторная
попытка с текстом ошибки → деградация в текстовый ответ.

### Р3. Безопасность — confirm-before-execute для всех записей
Сейчас инвариант «модель без инструментов и side effects» (`build-prompt.ts:11-16`) —
это и есть защита от prompt injection: данные банка (названия мерчантов!) попадают
в промпт. Даём инструменты — инвариант ломается. Компенсация:

- **Read-инструменты** (дашборд, поиск транзакций, отчёты) выполняются автоматически.
- **Write-инструменты** рендерят **карточку подтверждения** в чате (что, сколько,
  куда) — выполняются только по тапу пользователя. Никогда автоматически.
- Все write идут через существующие REST-эндпоинты → аудит и undo даром.
- Данные из БД в промпте остаются внутри существующего data-fence.

### Р4. UX — отдельный chrome-less роут + переключатель режима
- Новый route group `frontend/app/chat/` со своим минимальным layout
  (без Sidebar/TopBar/MobileBottomBar) — чище, чем дырявить guards в root layout.
  `AppChrome.shouldHideChrome` + guards для TopBar/MobileBottomBar.
- Вход: пункт «Режим чата» в сайдбаре + кнопка в TopBar; выход — кнопка
  «Полный интерфейс» в самом чат-режиме.
- Выбор режима сохраняется (localStorage) — при следующем входе пользователь
  попадает сразу в чат.
- В чат-режиме: приветствие, чипы быстрых действий («Добавить расход»,
  «Загрузить выписку», «Сколько я потратил в этом месяце?»), карточки
  результата (мини-сводка расхода, мини-отчёт), карточки подтверждения.

## Набор инструментов MVP

Read (авто): `get_dashboard`, `get_trends`, `list_transactions` (+semantic search
через `/ai-analysis/search`), `list_categories`, `spend_report`.
Write (с подтверждением): `create_expense` (через `POST /data-entry` либо
`submitManualExpense`), `set_transaction_category` (`PUT /transactions/:id` /
`bulk-update`), `split_transaction` (`POST /transactions/:id/split`).
UI-действия: `open_upload_statement` (диспатч `STATEMENTS_OPEN_UPLOAD_MODAL_EVENT`
— загрузка файла остаётся нативным диалогом; в chrome-less режиме — свой
упрощённый аплоадер поверх `uploadStatementFiles`).

Вне MVP: webhooks, payables, budgets, subscriptions, custom tables, members.

## Этапы

### Этап 0 — Спайк: качество constrained intents на локальной модели
Вне продового кода: прогнать `Qwen3.5-4B` (дефолт каталога) на 15–20 русских
фразах («добавь расход 5000 тенге на такси вчера», «покажи траты за июль»,
«разбей эту транзакцию пополам») через схему из Р2.

**Verify:** ≥80 % фраз дают валидный интент с корректными параметрами.
Если нет — MVP сужаем до read-инструментов + чипов, а write уводим за облачный
провайдер (Р1); обсуждаем перед продолжением.

### Этап 1 — Backend: роль `tool` и идемпотентность
- `ai-chat` DTO/entity: роль сообщения `'user' | 'assistant'` → + `'tool'`,
  опциональное поле `actionPayload` (jsonb) для карточек. Миграция.
- `IdempotencyService` подключить к `POST /data-entry` и
  `POST /statements/manual-expense` (сейчас его читает только upload) —
  агент с ретраями обязан слать `idempotency-key`.

**Verify:** unit-тесты на оба эндпоинта с повторным ключом → 200 с тем же
результатом, без дубликата; существующие specs зелёные;
`npm --prefix backend run typecheck`.

### Этап 2 — Frontend: tool registry
Новый модуль `frontend/app/chat/tools/`:
`{ name, description, schema (zod), kind: 'read' | 'write' | 'ui', execute }`.
Схемы портируем из `mcp-server/src/tools/*`; `execute` — тонкие обёртки над
`apiClient` и существующими сервис-функциями. Генерация текстового описания
инструментов для системного промпта из этого же реестра.

**Verify:** unit-тесты (vitest) на валидацию параметров каждого инструмента
и на генерацию описания; type-check.

### Этап 3 — Агентный цикл в useChat
- Расширить `send()`: ответ модели парсится по схеме Р2; read-интент →
  выполнить → результат в промпт → финальный ответ; write-интент → карточка
  подтверждения (pending action в стейте) → по тапу `execute` → результат в чат.
- Ретрай невалидного интента (1 раз), деградация в текст.
- Персистенция tool-ходов через новую роль.

**Verify:** vitest на цикл с замоканным engine (валидный/невалидный интент,
подтверждение/отмена, ретрай); type-check.

### Этап 4 — Компоненты карточек
`ActionConfirmCard` (сумма/дата/категория + Подтвердить/Отменить),
`ActionResultCard` (успех/ошибка + ссылка на сущность), `MiniReportCard`
(топ-категории/суммы). Вставляются в ленту `ChatTab` между `:124` и `:126`.

**Verify:** stories/vitest на рендер каждой карточки; визуальная проверка
в браузере.

### Этап 5 — Chrome-less роут и переключатель режима
- `app/chat/layout.tsx` + `page.tsx` (welcome, чипы, чат на всю высоту).
- `shouldHideChrome` + guards TopBar/MobileBottomBar для `/chat`.
- Пункт навигации + кнопка выхода из режима; persistence выбора режима;
  редирект при входе, если режим включён.
- i18n: все новые строки в `*.content.ts` на **21 локаль**.

**Verify:** `/chat` без хрома на desktop и mobile viewport; переключение
туда-обратно; `intlayer build` зелёный; type-check + lint (Biome **и** ESLint).

### Этап 6 — Сквозная проверка и полировка
Ручной прогон в браузере ключевых сценариев: вопрос о тратах → ответ с цифрами;
«добавь расход…» → карточка → подтверждение → расход виден в Statements;
категоризация; загрузка выписки. Пустые состояния (модель не установлена →
ведём в установку модели прямо из чата).

**Verify:** сценарии проходят end-to-end на dev-стенде; `npm test` зелёный.

### Этап 7 (опционально, отдельно) — облачный провайдер BYO-key
Backend-прокси completions (ключ шифруется в настройках workspace, SSE),
переключатель провайдера в настройках, полноценный multi-step tool calling.
Отдельный план после обкатки MVP.

## Риски

1. **Качество 4B-модели** — главный риск; снимается этапом 0 до основной работы.
2. **Prompt injection через данные банка** — write только через подтверждение (Р3).
3. **Дубликаты при ретраях** — идемпотентность (этап 1) до включения write-инструментов.
4. **21 локаль** — объём строк заметный; чипы и карточки держим лаконичными.
5. **Загрузка файлов в чат-режиме** — в MVP упрощённый аплоадер, без drag&drop-паритета.
