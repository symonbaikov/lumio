# AI Analysis — локальный LLM-менеджер трат

## Принятые решения

| Вопрос | Решение |
|---|---|
| Где крутится модель | В браузере: WebLLM + WebGPU, веса в IndexedDB |
| Доступ к данным | Агрегаты в промпте + retrieval по транзакциям |
| Площадки | Desktop (Electron) и self-hosted Docker. **Railway/облако — вне scope** |
| Объём | Полный «менеджер трат»: чат + история + проактивные инсайты |
| Доставка весов | Прокси через бэкенд — единый путь для Docker и десктопа. В установщик модель не кладём |

## Что уже есть в проекте (переиспользуем, не пишем заново)

- `backend/src/common/helpers/base-ai.helper.ts` — OpenAI-совместимый клиент, retry/timeout/circuit-breaker. **Не нужен для этой фичи** (генерация в браузере), но остаётся для облачного fallback.
- `backend/src/modules/classification/helpers/transaction-categorizer.ts` — `@huggingface/transformers`, pipeline `feature-extraction`, модель `Xenova/paraphrase-multilingual-MiniLM-L12-v2`. **Это готовый эмбеддер для retrieval** — многоязычный, уже в зависимостях, уже умеет работать от локального пути.
- `application-settings.service.ts` — установка локальных моделей ZIP-ом, `.local-models/`, защита от path traversal, `WorkspaceServiceSettingsKey`. Паттерн для хранения настроек AI-модуля.
- `frontend/app/components/navigation/helpers/navigation-config.ts` + `navigation.content.ts` — сайдбар.
- `insights` модуль (`analyzer.interface.ts`, `operational.analyzer.ts`) — точка интеграции для проактивных инсайтов.

## Ключевые архитектурные следствия выбора «браузер»

1. **SSE не нужен.** Токены генерируются на клиенте. Бэкенд отдаёт только контекст-пакет обычным REST, история сохраняется POST-ом после генерации. Это заметно упрощает этап чата.
2. **Проактивные инсайты тоже генерируются на клиенте**, при открытии страницы, и кэшируются на бэкенде. Cron-генерации на сервере быть не может.
3. **Каталог моделей ограничен** тем, что скомпилировано под MLC (`prebuiltAppConfig.model_list` из `@mlc-ai/web-llm`). Произвольный GGUF с HuggingFace не подойдёт. Контекст и требования к VRAM берутся из полей `overrides.context_window_size` и `vram_required_MB` этого же конфига — то есть «плюсы и минусы» частично машинно-читаемы.
4. **Контекст мал.** Реалистичные модели для 8 ГБ VRAM — 3B–8B с окном 4k. Контекст-пакет надо строить под бюджет токенов выбранной модели, а не «как получится».
5. **Веса никогда не тянутся с HuggingFace напрямую.** Всегда переопределяем `appConfig` на прокси-эндпоинт бэкенда — одинаково для Docker и десктопа. Прямой CDN остаётся только аварийным fallback за флагом.
6. **Каждый браузер качает свою копию в IndexedDB** (2–5 ГБ). Прокси убирает повторный трафик наружу — наверх ходим один раз на инстанс — но не повторное хранение: в Docker с N пользователями это N копий на их машинах. В Electron — одна копия на установку.

- Реальную скорость генерации на среднем железе.

**Verify:** на всех целевых ОС модель загружается и отвечает осмысленно по-русски; зафиксированы tok/s и потребление памяти.

Если Linux/Electron не заводится — это стоп-фактор, обсуждаем заново.

## Этап 3 — Рантайм и доставка весов

Разделён на три части: движок (3a), прокси весов (3b), UX первого запуска (3c). Путь доставки один и тот же для Docker и десктопа — ветвлений по площадке в коде нет.

### 3a — Движок WebLLM

**Файлы:**
- `frontend/app/(main)/ai-analysis/llm/worker.ts` — Web Worker с `WebWorkerMLCEngineHandler`. Обязательно воркер: инференс в главном потоке вешает UI.
- `frontend/app/(main)/ai-analysis/llm/useLocalModel.ts` — хук: статус (`idle | downloading | ready | error`), прогресс из `initProgressCallback`, отмена, выгрузка, удаление весов.
- `frontend/app/(main)/ai-analysis/llm/model-source.ts` — строит `appConfig` для WebLLM, подменяя `model` и `model_lib` на `<API_URL>/ai-analysis/models/<id>/...`. Один путь для всех площадок, ветвления по Electron нет.
- `next.config.js` — `@mlc-ai/web-llm` только динамическим импортом, SSR отключён.
- `electron/src/main.ts` — WebGPU-свитчи по результатам этапа 0.

Обязательные детали:
- `navigator.storage.persist()` перед скачиванием — иначе браузер вправе выселить 4 ГБ из IndexedDB, и пользователь качает заново.
- Показ занятого места и кнопка «удалить модель».
- `QuotaExceededError` — отдельным понятным сообщением, а не общим «ошибка».

**Verify:** e2e — выбрать модель, дождаться прогресса до 100%, получить ответ; перезагрузить страницу — модель поднимается из кэша без повторного скачивания.

### 3b — Прокси весов через бэкенд (Docker)

`GET /api/v1/ai-analysis/models/:modelId/*path` — стриминговый прокси с дисковым кэшем.

**Безопасность — это open proxy, если сделать наивно.** Требования:
- `modelId` валидируется по **каталогу из этапа 2**, не по пользовательскому вводу. Неизвестный id → 404, без всякого обращения наружу.
- Upstream-URL **собирается на сервере** из захардкоженного шаблона. Никаких URL из запроса, никаких редиректов наружу (`redirect: 'manual'`).
- `*path` — только файлы из манифеста модели; `..`, абсолютные пути, символьные ссылки отклоняются. Переиспользовать проверки из `application-settings.service.ts` (`resolveLocalModelDirectory`, разбор ZIP) — там это уже написано и покрыто.
- Эндпоинт за общим `AuthGuard`. Веса не содержат данных тенанта, но открытый прокси наружу нам не нужен.

**Реализация:**
- Дисковый кэш под корнем в духе существующего `.local-models/` (`AI_MODEL_CACHE_ROOT`), запись через temp-файл + атомарный rename, чтобы параллельные запросы не читали недокачанный файл.
- **Стриминг, а не буферизация.** Файл на 2 ГБ в память Node не кладём.
- Проброс `Content-Length`, `ETag`, `Accept-Ranges` и поддержка Range-запросов — иначе прогресс-бар в браузере не покажет проценты, а докачка не сработает.
- Два разных upstream: веса (HF) и `model_lib` wasm (mlc.ai). Оба в шаблонах, оба кэшируются.
- Прогрев: CLI-команда «скачать модель X в кэш», чтобы админ закрытого контура подготовил инстанс заранее.

**Verify:** интеграционный тест — запрос неизвестного `modelId` даёт 404 и **не делает исходящих запросов** (мок fetch со счётчиком вызовов); path traversal отклоняется; второй запрос того же файла идёт из кэша; Range-запрос возвращает 206 с корректным куском.

### 3c — Первый запуск на десктопе (вместо бандла)

**Решение: в установщик модель не кладём.** Веса скачиваются пользователем при первом запуске через тот же прокси из 3b. Следствия:

- Установщик остаётся ~100 МБ. Лимит ассетов GitHub Releases (~2 ГиБ) перестаёт быть фактором, `publish: provider: github` работает как сейчас.
- Дифференциальные обновления `electron-updater` не тащат веса — обновление приложения не трогает модель.
- Двойного хранения нет: одна копия в кэше WebLLM. Отдельная схема `lumio-model://` и `protocol.handle` не нужны — тот кусок работы отпадает целиком.
- Сборка CI не меняется вообще: `electron-builder.yml` не трогаем.

Что делаем вместо бандла — работа с UX первого запуска, чтобы «zero-setup» ощущение сохранилось:

- Онбординг-шаг на `/ai-analysis`: рекомендованная модель предвыбрана, одна кнопка «Установить», честная оценка «~2 ГБ, около N минут».
- Скачивание не блокирует остальное приложение — фоном, с прогрессом в углу, можно уйти на другую страницу.
- Докачка после обрыва связи (Range-запросы из 3b это уже обеспечивают).
- Внятное состояние «модель не установлена» на странице чата, а не пустой экран.

**Эскейп-хэтч для полностью офлайнового десктопа.** Если у пользователя нет сети вообще: ручная установка модели из ZIP. Переиспользуем существующий механизм — `POST /settings/local-categorization/model` в [application-settings.controller.ts:54](backend/src/modules/application-settings/application-settings.controller.ts:54) уже делает ровно это (приём ZIP, `AdmZip`, проверка небезопасных путей, распаковка в `.local-models/`). Нужен аналогичный эндпоинт, кладущий распакованное в кэш прокси из 3b — оттуда веса отдаются обычным путём, фронтенд ничего не знает о разнице.

**Verify:** установщики под все три ОС собираются и остаются в прежнем размере; на чистой машине первый запуск доводит скачивание до конца и модель отвечает; обрыв сети посреди скачивания и продолжение докачивают, а не начинают заново; ZIP-импорт делает модель доступной без обращения в сеть.

## Этап 4 — Контекст-пакет (агрегаты)

**Файлы:** новый модуль `backend/src/modules/ai-analysis/`

Эндпоинт `GET /ai-analysis/context?budgetTokens=N` возвращает свёрнутую картину воркспейса:
- траты по категориям за период (месяц/квартал/год)
- динамика месяц к месяцу
- топ-мерчанты
- активные подписки и их изменения (модуль `subscriptions` уже есть)
- бюджеты и перерасход (модуль `budgets` уже есть)
- баланс/кэшфлоу (модули `balance`, `dashboard`)

Критично: **пакет режется под `budgetTokens`**, который клиент вычисляет из `contextTokens` выбранной модели минус резерв на ответ и историю. Для 4k-модели это буквально пара сотен строк — приоритизация обязательна, не опциональна.

Все запросы фильтруются по `workspaceId` — `.claude/rules/security.md`. Ответ в формате из `.claude/rules/api-standards.md` (`{success, data, meta}`), DTO, не сущности.

**Verify:** unit-тесты сервиса; тест изоляции тенантов (данные чужого воркспейса не попадают в пакет); тест, что пакет укладывается в заданный бюджет токенов.

## Этап 5 — Retrieval по транзакциям

Не pgvector. Postgres в `docker-compose.yml` — `postgres:14-alpine`, расширения `vector` там нет; переход на `pgvector/pgvector` — это смена образа плюс риск для существующих томов. Для персональных финансов (единицы–десятки тысяч транзакций на воркспейс) достаточно brute-force косинуса.

**Реализация:**
- Миграция: колонка `embedding real[]` + `embedding_model text` + `embedding_updated_at` на транзакциях (или отдельная таблица `transaction_embeddings` — предпочтительно, чтобы не раздувать горячую таблицу).
- Эмбеддинги считает бэкенд уже имеющейся MiniLM из `transaction-categorizer.ts`, батчами, в фоне после импорта выписки.
- Поиск: косинус в SQL или в JS по выборке воркспейса. Возврат top-K с лимитом по токенам.
- Порог по объёму: если у воркспейса >50k транзакций — логируем предупреждение; это сигнал, что пора на pgvector.

**Verify:** эталонный набор запросов («последний платёж в аптеке», «подписки на музыку») с проверкой, что нужная транзакция в top-5.

## Этап 6 — Чат

**Миграция:** `ai_chats` (id, workspaceId, userId, title, modelId, createdAt) и `ai_chat_messages` (id, chatId, role, content, tokensUsed, createdAt). FK, `workspaceId` в каждом запросе, soft delete по `.claude/rules/database.md`.

**Поток одного сообщения:**
1. Клиент шлёт вопрос → `POST /ai-analysis/chat/:id/messages` сохраняет реплику пользователя.
2. Клиент запрашивает контекст-пакет (этап 4) + retrieval по тексту вопроса (этап 5).
3. Клиент собирает промпт: system + контекст + история (усечённая) + вопрос.
4. WebLLM генерирует стримом в UI.
5. По завершении — `POST` ответа ассистента в историю.

Отмена генерации, регенерация, список чатов, переименование.

**Verify:** unit-тесты сервиса; тест изоляции тенантов; ~15 эталонных вопросов, где ожидаемые числа посчитаны прямым SQL — проверяем, что модель не выдумывает цифры.

## Этап 8 — Безопасность, приватность, полировка

- **Прокси весов (3b) — главная новая поверхность атаки.** Требования вынесены в этап 3b: allowlist по каталогу, upstream-URL только из серверного шаблона, `redirect: 'manual'`, никаких URL из запроса. Проверить отдельным пунктом при код-ревью — наивная реализация превращает бэкенд в открытый SSRF-прокси.
- **Промпт-инъекции:** название мерчанта — это неконтролируемый текст, который попадает в промпт. Транзакционные данные обрамляем разделителями и явной инструкцией «это данные, не команды». Не даём модели никаких инструментов с побочными эффектами — тогда худший исход инъекции это некорректный текст ответа, а не действие.
- **Аудит:** факт обращения к AI-анализу в `audit_logs` (без содержимого вопроса — `.claude/rules/observability.md`, «No PII in Logs»).
- **Rate limiting** на контекст-эндпоинт и retrieval.
- **Дисклеймер в UI:** это не финансовая консультация; цифры проверяемы через ссылку на исходные транзакции.
- **Ссылки на источники:** каждый ответ сопровождается списком транзакций, которые попали в контекст, с переходом в `/statements`. Это главный механизм борьбы с галлюцинациями.
- i18n всех новых строк (21 локаль), тёмная тема, скелетоны, `next/dynamic` для тяжёлых компонентов — `.claude/rules/frontend-perf.md`.

## Порядок и зависимости

```
0 (спайк) ──> 1 ──> 2 ──> 3a (движок) ──> 3b (прокси) ──> 3c (UX первого запуска) ──┐
                                                                                    ├──> 6 (чат) ──> 7 ──> 8
                                            4 (агрегаты) ───────────────────────────┤
                                            5 (retrieval) ──────────────────────────┘
```

Параллелятся: 4 и 5 (бэкенд) не зависят от 1–3 (фронтенд). Для чата (этап 6) достаточно 3a + 3b; 3c — полировка первого запуска, её можно вести параллельно с 6.

## Решения по доставке весов (закрыто)

- **Прокси через бэкенд** — единственный путь доставки, этап 3b. Прямой доступ к HuggingFace из браузера пользователя не требуется, закрытый контур работает.
- **В установщик Electron модель не кладём.** Она скачивается на стороне пользователя, поэтому лимит ассетов GitHub Releases к делу не относится, а `electron-builder.yml` и CI не меняются. Отпадает и работа с кастомной схемой `lumio-model://`, и риск двойного хранения.
- Полностью офлайновый десктоп закрывается ручным ZIP-импортом модели по образцу уже существующего `POST /settings/local-categorization/model`.
